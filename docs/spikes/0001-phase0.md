# Spike 0001 — Phase 0: toolchain and WSL2 Arma tier

**Run:** 2026-07-30 · **Issue:** [#2](https://github.com/andrewesweet/arma-cti/issues/2) · **Decides:** [ADR-0006](../adr/0006-wsl2-linux-server-test-tier.md)

## Verdict: GO — the loop is viable and fast; the unattended-client path is not yet solved

The development loop works and is fast. A WSL2-native Arma 3 Linux dedicated server boots a
Stratis mission in ~20 s, the Rust shim round-trips a payload to a Python daemon in
**0.37–0.65 ms**, and the whole no-Arma gate (`just check` + `just unit`) runs in **under a
second**. Both shim artefacts build from this box: the Linux `.so` natively and the Windows
`.dll` through `cargo-xwin`.

**The Windows-client join works.** A Windows Arma 3 client on the host reached the WSL2 server,
picked a slot, spawned, and ran `init.sqf` — the server logged both `player_connected name=andre
… jip=true` and the client's own report back. So the play path in ADR-0006 holds.

Two items are not proven:

- **Blocking for the Arma test tier:** no client, headless or human, enters the mission without a
  human clicking a slot in the role-selection lobby. That is fine for play and fatal for an
  unattended harness. Detail in [§5](#5-open-no-unattended-client-gets-past-role-selection).
- **Unexplained:** the Windows client desynced once in the mission — repeating "No message
  received after N seconds" while the server sat at 99 fps and logged nothing. [§6](#6-open-windows-client-desync).

ADR-0006's fallback (orchestrating the Windows server binary from WSL2) is **not** needed on the
evidence here. Nothing found argues against the Linux server specifically: the lobby behaviour is
the engine's, and would be identical under the Windows server binary.

### One toolchain defect found and fixed

`format-on-edit.py` invoked `rustfmt --edition 2021` while the shim crate is edition 2024, so the
hook reformatted files into a state `cargo fmt --check` then rejected. Fixed to `--edition 2024`.
Worth a retro note: an auto-formatter hook that disagrees with the gate is worse than no hook.

## 4. Extension RPC — the numbers ADR-0004 and ADR-0005 rest on

Three consecutive clean runs. `bench` measures inside the extension (SQF's `diag_tickTime` is
frame-quantised and too coarse for a single call); FFI cost is measured in SQF by amortising 2000
calls across one frame; callback latency is measured in SQF because it deliberately spans frames.

| Measurement | Run 1 | Run 2 | Run 3 |
|---|---|---|---|
| Server host up (s) | 11.3 | 9.3 | 9.3 |
| **Mission running (s)** | 20.3 | 20.9 | **19.6** |
| Headless client network join (s) | 22.6 | 20.6 | 24.1 |
| `callExtension` FFI, no I/O (µs/call) | 0.50 | 0.50 | 0.50 |
| **Daemon round trip, connection per call** — p50 (ms) | 1.34 | 1.62 | 1.61 |
| … min / p95 / max (ms) | 0.90 / 2.15 / 2.89 | 1.17 / 3.18 / 4.83 | 1.15 / 2.42 / 2.54 |
| **Daemon round trip, kept-alive connection** — p50 (ms) | **0.51** | 0.65 | 0.45 |
| … min / p95 / max (ms) | 0.27 / 0.77 / 1.98 | 0.33 / 1.06 / 1.59 | 0.24 / 0.75 / 1.58 |
| **`ExtensionCallback` end to end** — p50 (ms) | 17.0 | 13.0 | 10.0 |
| … min / max (ms) | 8.0 / 18.0 | 9.0 / 20.0 | 9.0 / 19.0 |
| Server peak RSS (MiB) | 1117 | 1116 | 1117 |
| Headless client peak RSS (MiB) | 897 | 897 | 897 |
| Server FPS (`-limitFPS=100`) | 97.6 | 99.4 | 100.6 |

Reading these:

- **`callExtension` itself is free.** 0.50 µs per call means the engine boundary never needs
  budgeting. Design against the daemon's cost, not the FFI's.
- **Keep the connection.** Reusing one TCP connection is roughly 3× faster than reconnecting per
  call (0.45–0.65 ms vs 1.34–1.62 ms p50). The shim should hold a persistent connection and
  reconnect on failure, as the spike shim already does.
- **The callback path costs a frame, not a millisecond.** 10–17 ms p50 against a sub-millisecond
  transport: the engine drains `ExtensionCallback` on its own cadence, so latency is frame-bound
  and independent of daemon speed. Fine for Commander decisions on a 60 s income tick; do not put
  anything per-frame behind it.
- **Memory is not a constraint.** Server plus headless client peak at ~2 GiB of the VM's 11 GiB.

Payload integrity was checked verbatim, not just by timing: a JSON object sent from SQF came back
through the daemon with its fields intact, including the daemon's own receive/send timestamps.

### Findings the research reports did not have

1. **`arma-rs` needs `.allow_no_args()`.** Without it, `"cti_shim" callExtension "ping"` returns
   an empty string and only the array form reaches a handler. Silent, and it cost time.
2. **The Linux server appends `_x64` exactly as Windows does.** SQF says `"cti_shim"`; the engine
   opens `cti_shim_x64.so`. A file named `cti_shim.so` is never found, and
   `"cti_shim_x64" callExtension` fails because the engine appends a second `_x64`.
3. **HEMTT cannot pack missions.** `hemtt utils pbo` only extracts, inspects and unpacks. Missions
   need their own packer, so `tools/pack_pbo.py` was written; output is verified by
   `hemtt utils pbo inspect`, which validates the SHA-1 trailer.
4. **Missions must be PBOs, not folders,** for the Arma tier. An unpacked mission folder cannot be
   transmitted to a joining client.
5. **`banned_commands` works as the SQF contract's enforcement.** A deliberate bare `random`
   produced `error[L-S09]: 'random' is banned by the project` and exit 1. CLAUDE.md's "never
   introduce a bare `random` or `sleep`" rule is now mechanical, and needs no grep lint.
6. **SQF-VM's exit-code trap is real, exactly as researched.** A runtime type error exits **0**;
   only parse errors exit 255. Any future SQF-VM tier must parse stdout and synthesise its own
   verdict.

## 5. Open — no unattended client gets past role selection

**Symptom.** The headless client starts, connects, and is accepted: the server logs
`Player headlessclient connected (id=HC…)` about 20–24 s after launch. It then stops. It never
loads the mission, `init.sqf` never runs on it, `onPlayerConnected` never fires for it, and
`entities "HeadlessClient_F"` and `allPlayers` both stay empty server-side.

**What this actually is.** A real Windows client launched with
`-connect=… -port=… -password=…` does the same thing: it connects and then **sits in the
multiplayer role-selection lobby**, waiting for a human to pick a slot and press OK. Only after
that click does it enter the mission and run `init.sqf`. Every symptom above is what that lobby
looks like from the server when the client has no UI to click with.

So this is not a headless-client defect and not a Steam-identity problem — the earlier leading
hypothesis, which the human-client observation supersedes. It is the ordinary Arma multiplayer
join flow, which assumes a human. The real question is narrower and better posed: **how does an
unattended client get past role selection?** Working headless-client deployments plainly manage
it, so a mechanism exists; we have not found it. Research is in flight
(`docs/research/headless-client-join.md`).

`joinUnassigned = 1` is set and is not sufficient. Neither is removing the human playable slot so
that only the `HeadlessClient_F` slot remains — tested, no change.

**Reproduction.** `./spike/run.sh`; look for `hc_joined=true` alongside
`WARN headless_client_never_ran_mission_scripts`. Or `./spike/run.sh --hold` and connect any
client: it will stop at role selection.

**A lead worth following before building anything bespoke.** Both the Windows client and the Linux
server binary contain the startup parameter `-autotest=<config>` (plus `-autotestSingleMission=`)
and an `isAutotest` script command. The binary's own error strings show the config takes a
`TestMissions` class of subclasses, and that it emits `<AutoTest result="…">` with `EndMode`,
`Campaign` and `Mission` fields — i.e. Bohemia ships an unattended mission runner whose verdict is
the mission's end type. Passing it to the dedicated server in server mode did nothing, so it is
presumably a singleplayer/campaign facility, which would make it a separate tier rather than a
replacement for the MP one. Being chased in
`docs/research/arma-automated-testing-prior-art.md`.

**Eliminated by experiment** — each of these was tested and made no difference:

| Hypothesis | Result |
|---|---|
| Mission is an unpacked folder | Packed to PBO; no change |
| Client lacks `-filePatching` | Added; server answered `does not accept the client's current filePatching setting`; no change |
| BattlEye holding the client | `battlEye = 0`; no change |
| No headless-client slot in `mission.sqm` | Added a `HeadlessClient_F` entity; server's role count went 1 → 2, confirming the slot is real; no change |
| Port collision with the Windows client (2302–2306, shared under mirrored networking) | Moved the tier to 2402–2406; no change — but kept, see below |
| Server has no password | Set one and passed `-password`; no change |
| `headlessClients[]` whitelist wrong | Removing it is *worse*: `Client kicked due to failed Steam checks: Invalid ticket`. The whitelist is required |
| `disabledAI = 1` deleting the slot | Set to 0; no change |
| Loopback ambiguity under mirrored networking | Connected over the LAN IP 192.168.1.36 instead; no change |
| `-autoInit` assigning roles before the client arrives | Ran without `-autoInit`: the server selects the mission when the headless client connects (`Mission spike.Stratis read from bank.`) but never starts it; no change |
| Client stuck on the briefing screen | `briefing = 0; debriefing = 0;`; no change |
| `steam_appid.txt` wrong (SPOTREP #00119 warns of this) | Contains `107410`; set to `233780` and back; no change |

**A hypothesis now demoted.** In the run without `-autoInit` the server emitted
`Server error: Player without identity headlessclient (id 336778391)`, which alongside the Steam
kick above suggested that a Steam-less client cannot be assigned a role. That was the leading
theory until the Windows client — which has a full Steam identity — stopped in exactly the same
place. Steam identity is therefore not the explanation, though the message remains unexplained.
It is recorded here so it is not re-derived later.

**Not a blocker for Phase 1.** Server-side logic, the snapshot store, the planner and the shim are
all exercisable without an unattended client. It blocks the acceptance tier that simulates
players, so it must be resolved before that tier is built, not before Phase 1 starts.

## 6. Open — Windows client desync

Once in the mission the Windows client could not move and reported "No message received after
10/15/20/25… seconds" while remaining connected. The server was unaffected throughout: 99 fps, and
not one bandwidth, packet, timeout or disconnect message in its log.

Untested candidates, in the order worth trying:

1. **`localClient[]` includes the human's address.** The spike config lists `127.0.0.1`,
   `localhost` and the LAN IP, which grants unrestricted bandwidth. That setting is meant for a
   headless client on the same machine, not for a real player arriving across the mirrored-network
   boundary.
2. **`spike/basic.cfg` is hand-written and unvalidated.** `MaxMsgSend = 256`,
   `MaxSizeGuaranteed = 512`, `MaxSizeNonguaranteed = 256`. Testing with no `-cfg=` at all, on
   engine defaults, is the cheap discriminator.
3. **Mirrored-mode UDP may not sustain bidirectional game traffic.** Prior research verified single
   datagrams crossing in each direction; a continuous simulation stream is a different claim. If
   this is the cause it is the one genuinely serious finding against ADR-0006, so it must be
   distinguished from 1 and 2 before drawing any conclusion.

Not reproduced under automation yet, because reaching the in-mission state needs the manual slot
click of §5.

## 7. Constraints this spike adds

1. **The test tier must not use ports 2302–2306.** Under `networkingMode=mirrored` the Windows
   host and the WSL2 VM share a port space, so a spike server on 2302 collides with the Windows
   Arma client. Observed live: a headless client of ours appeared in the human's Windows Arma
   session. The tier is fixed at 2402–2406 (Bohemia wants ≥100 between server port sets).
2. **Steam allows one session per account.** The `idiomonline` server account and the human's
   playing account must stay distinct. The Windows client does *not* need closing for a join test,
   since the accounts differ and the port blocks no longer overlap.
3. **Missions ship as PBOs.** `just build-missions` packs `missions/*/` via `tools/pack_pbo.py`.
4. **`-profiles=` is broken on Linux.** Profiles must live in `~/.local/share/Arma 3` and
   `~/.local/share/Arma 3 - Other Profiles`; the harness creates both.
5. **The Windows client is drivable from WSL2.** `powershell.exe Start-Process` over the interop
   boundary launches `arma3_x64.exe` with `-connect`/`-port`/`-password`, and its RPT is readable
   at `/mnt/c/Users/<user>/Documents/Arma 3/`. Useful for play-session automation and perceptual
   checks; it does not solve §5, because the client still stops at role selection.
