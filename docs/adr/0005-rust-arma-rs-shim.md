# Extension shim in Rust using arma-rs

The Arma-to-daemon shim is written in Rust on the `arma-rs` crate (extension ABI, argument handling, ExtensionCallback, single codebase for .dll and .so, native `cargo test`), replacing the design doc's C++/Catch2 choice. Transport is TCP on 127.0.0.1 to the daemon (unix sockets do not cross the WSL2/Windows boundary), JSON payloads for MVP. The shim stays domain-agnostic: transport, framing, retry, idempotent delivery, callback dispatch — payloads are opaque, so domain changes never require a shim rebuild.

Amended 2026-07-30 (phase-0 measurements, docs/spikes/0001-phase0.md §4): the shim holds one persistent TCP connection and reconnects on failure. Reusing the connection is ~3× faster than connecting per call (0.45–0.65 ms vs 1.34–1.62 ms p50 round trip), and the persistent connection is where retry and idempotent delivery live. Per-call connections are rejected.

Amended 2026-07-30, engine limits from the vendored wiki (`commands/callExtension.wiki`, `topics/Extensions.wiki`) that bind this design:

- **A `callExtension` return is capped at 10,240 bytes**; multipart results are the extension author's problem. Orders fit in one call; snapshot save/load (ADR-0003/0008) will not — a chunking protocol must be designed before Phase 2, and it lives in the shim's framing layer, not in SQF.
- **A blocking `callExtension` that exceeds 1000 ms trips the engine's `EXECUTION_WARNING_TAKES_TOO_LONG`** (server-tunable via `callExtReportLimit`) and stalls the frame for the duration. The synchronous path is reserved for sub-millisecond round trips; anything that can be slow (planner, persistence) goes through the async path and returns via callback.
- **Callback delivery is at-most-once across mission boundaries.** Callbacks fired before an `ExtensionCallback` handler exists sit in the engine buffer; removing all handlers or a mission restart clears the buffer. Idempotent delivery therefore requires the SQF handler to be registered before the daemon is told to push, and daemon-side acknowledgement/replay for anything that must not be lost. (arma-rs already handles the documented buffer-full retry: negative return, retry until accepted.)

Amended 2026-07-31 (#15): **the Observation is pull-only, on the synchronous path.** The world already reports what only it can see every few seconds; the whole strategic picture (`CONTEXT.md`: **Observation**) is the reply to that report rather than anything the daemon pushes. The daemon therefore has no way to volunteer one, and cadence belongs entirely to the game.

The split is by kind, not by convenience. **Effects are events**: an accepted Purchase that never spawns its Squad is lost work, so effects ride the outbox's acknowledgement and replay over the callback path, exactly as the limit above requires. **An Observation is state**: losing one costs nothing, because the next report carries the whole picture again and supersedes it. Replaying a stale one would be worse than dropping it. So the Observation needs neither acknowledgement nor replay — not because the guarantee was waived, but because a synchronous reply either arrives or visibly fails, which is stronger than at-most-once.

Two consequences bind later work:

- **Freshness is the report interval**, and nothing can ask for a fresher picture. #16's planner and #18's map UI both read a picture up to one interval old, while a Command's *judgement* still returns immediately — two latencies on one screen, to be designed for rather than discovered.
- **The whole picture must fit one return**, so the 10,240-byte cap above binds the Observation directly. Measured: the ceiling is about 35 Squads a side on any map, because a Squad costs ~109 bytes and Objective count barely registers. `cti_fnc_presenceReport` fails the run at nine tenths of the cap rather than letting the engine truncate in silence. #26 records the levers.

Amended 2026-07-31 (ADR-0018): **Effects ride poll-and-ack on the synchronous path, not the callback path.** Two clauses above are superseded: "effects ride the outbox's acknowledgement and replay over the callback path", and the routing of the planner through the async path — the planner answers inside the synchronous `observe` reply (746 µs p50, docs/spikes/0002-two-commanders.md), and effects are drained by `cti_fnc_effectPump` polling `rpc_keepalive`, acknowledged only after application. The at-most-once callback rule above still binds whatever does use the callback path; the async path itself is reserved for genuinely slow single calls, Phase-2 snapshot save/load above all, and before it carries production work `rpc_async` must take its own connection rather than sharing the persistent connection's mutex — a slow async call as written would block every synchronous judgement behind it. That requirement travels with this section's existing "chunking before Phase 2" gate. Numbers, tuning lever and overturn conditions: ADR-0018.

Rejected: **delta observations** — sending only what changed. It is the obvious size lever and it reverses this decision, because a delta is an event: losing one silently corrupts the picture instead of being superseded, which drags acknowledgement, replay and the callback path back in. If a later phase needs deltas, that is this amendment being revisited deliberately, with the reliability machinery that goes with it — not a size optimisation someone reaches for.
